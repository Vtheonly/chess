## 1. SYSTEM OVERVIEW & UI/UX CHARTER

### 1.1 Objective & Scope
This specification details the full-stack interactive application layer for **CaissaXAI**. It encompasses the responsive web frontend, real-time board rendering, interactive gameplay engines, WebSocket streaming protocols, move classification algorithms, game review dashboards, and the conversational coaching interface.

The system MUST provide three operational game modes:
1. **Mode A: Human vs AI (Coached Play):** Real-time interactive match against Stockfish at a selectable playing Elo, accompanied by instant per-move narrative coaching at a selectable explanation Elo.
2. **Mode B: AI vs AI (Self-Play Simulation):** Automated match between two configurable AI profiles (e.g., 800 Elo vs 1800 Elo) with live streaming commentary explaining the unfolding strategic dynamic.
3. **Mode C: Deep PGN Import & Game Review:** Batch analysis of imported games (PGN or FEN), featuring progress tracking, an interactive evaluation graph, move classification badges (Brilliant, Great, Best, Inaccuracy, Mistake, Blunder), and exportable annotated PGNs.

## 4. MOVE CLASSIFICATION & ACCURACY ALGORITHMS

### 4.1 Win Chance Conversion Formula
To calculate move accuracy and classification fairly across all phases of the game, raw centipawn evaluations must be converted to a **Win Chance Probability** $W \in [0.0, 1.0]$ using the Lichess/Stockfish sigmoid formula:

$$W = \frac{1}{1 + 10^{-\text{cp} / 400.0}}$$

If the evaluation is a mate score:
* $\text{Mate in } +N \implies W = 1.0 - (N \times 0.01)$
* $\text{Mate in } -N \implies W = 0.0 + (N \times 0.01)$

### 4.2 Move Classification Algorithm
For a move played at ply $P$, calculate $\Delta W = W_{\text{after}} - W_{\text{before}}$ (from the perspective of the player making the move).

```
FUNCTION classify_move(board_before, played_move, best_move, eval_before, eval_after, see_score):
    W_before = win_chance(eval_before)
    W_after = win_chance(eval_after)
    delta_W = W_after - W_before  # Negative value represents accuracy drop

    # 1. Check for BEST or BOOK
    IF played_move == best_move:
        RETURN "BEST"
        
    # 2. Check for BRILLIANT
    # Definition: Material sacrifice (SEE < -150) that is either the best move 
    # or maintains win chance within 3% of best move.
    IF is_sacrifice(board_before, played_move) AND see_score < -150 AND delta_W >= -0.03:
        RETURN "BRILLIANT"
        
    # 3. Check for GREAT
    # Definition: The ONLY move that preserves a winning/equal position when all other moves lose >20% win chance.
    IF is_only_viable_move(board_before, played_move, second_best_delta_W) AND delta_W >= -0.02:
        RETURN "GREAT"

    # 4. Standard Win Chance Drop Classifications
    IF delta_W >= -0.02:
        RETURN "EXCELLENT"
    ELSE IF delta_W >= -0.05:
        RETURN "GOOD"
    ELSE IF delta_W >= -0.10:
        RETURN "INACCURACY"
    ELSE IF delta_W >= -0.20:
        RETURN "MISTAKE"
    ELSE:
        # Check if a winning tactic was completely missed
        IF W_before >= 0.70 AND W_after < 0.50:
            RETURN "MISS"
        RETURN "BLUNDER"
```

### 4.3 Game Accuracy Percentage Formula
For a game with $N$ moves played by a player, calculate move accuracy percentage $A$ as:

$$A = 100 \times \frac{1}{N} \sum_{i=1}^{N} \left( 1.031668 \times e^{-0.04354 \times (\Delta W_i \times 100)^2} - 0.031668 \right)$$

## 5. MODE A: INTERACTIVE HUMAN VS AI (COACHED PLAY)

### 5.1 Workflow & Execution Loop
1. Player sets **Player Color** (White/Black), **AI Play Elo** (800–2800), and **Coach Elo** (800, 1200, 1500, 1800+).
2. If Player is Black, engine immediately executes first move as White.
3. Player selects square $\rightarrow$ Frontend highlights legal move target squares.
4. Player executes drag-and-drop or click-click move $\rightarrow$ Frontend optimistically plays move, triggers audio, and requests backend validation.
5. Backend verifies move legality, updates Stockfish analysis, extracts Layer 2 symbolic deltas, updates Layer 3 memory stack, calls Layer 5 LLM Narrator, and streams response back over WebSocket.
6. Frontend updates Board, Eval Bar, Move Table, and Narrative Panel simultaneously.
7. Backend triggers Stockfish to compute AI's counter-move (scaled to selected AI Play Elo via Stockfish UCI limit parameters `UCI_LimitStrength` and `UCI_Elo`).
8. AI move is executed on board $\rightarrow$ Audio plays $\rightarrow$ AI move analysis streams in.

### 5.2 Stockfish Elo Scaling Execution
To restrict Stockfish's playing strength for human play, the backend UCI process must be configured per move:

```python
# Stockfish UCI Strength Reduction Protocol
def configure_engine_elo(engine_process, play_elo: int):
    if play_elo >= 2800:
        engine_process.send_command("setoption name UCI_LimitStrength value false")
    else:
        engine_process.send_command("setoption name UCI_LimitStrength value true")
        engine_process.send_command(f"setoption name UCI_Elo value {play_elo}")
```

## 6. MODE B: AI VS AI (SELF-PLAY SIMULATION)

### 6.1 Workflow & Simulation Engine
1. User configures **White AI Elo** (e.g., 1000) and **Black AI Elo** (e.g., 2200).
2. User sets **Auto-Play Interval** (500ms to 5000ms).
3. User clicks **"Start Simulation"**.
4. Loop executes over WebSocket:
   * Backend requests Stockfish move for White (at White Elo).
   * Move executed $\rightarrow$ Full analysis + Layer 2 Deltas + Layer 5 Narrative generated.
   * Frame broadcast to client $\rightarrow$ Client animates move, updates eval bar, appends narrative.
   * Delay `autoPlaySpeedMs`.
   * Backend requests Stockfish move for Black (at Black Elo).
   * Repeat until Checkmate, Stalemate, or 3-fold repetition.
5. User can click **Pause**, **Step Forward**, **Step Backward**, or **Modify Elo Mid-Game**.

### 7.3 Dashboard Component Requirements
Upon 100% completion, the review screen renders:
1. **Header Cards:** Overall Accuracy % (White & Black), Total Blunders, Mistakes, Inaccuracies, Brilliant Moves.
2. **Interactive Eval Chart:** Line chart (Recharts) plotting Centipawn Eval vs Ply. Clicking any point on the chart jumps the board directly to that ply.
3. **Move Table with Badges:** Color-coded classification pills next to every SAN move.
4. **Annotated PGN Export Button:** Exports standard PGN string containing NAG symbols (`$1`, `$2`, `$3`, `$4`) and inline commentary brackets `{ [CaissaXAI]: ... }`.

## 13. ERROR HANDLING, EDGE CASES & RECOVERY (FRONTEND)

1. **WebSocket Disconnection Mid-Game / Mid-Review:**
   * Automatically attempt reconnection (max 5 retries, 2s backoff).
   * Maintain current PGN and local move history in Zustand `localStorage` persistence wrapper.
2. **Illegal Drag-and-Drop Attempt:**
   * Snap piece immediately back to original square.
   * Play silent error tick. Do NOT issue backend API request.
3. **Pawn Promotion User Gesture:**
   * When pawn reaches 8th/1st rank, pause move execution and display an inline modal over the target square asking the user to choose: Queen, Rook, Bishop, or Knight.
   * Append promotion letter (`q`, `r`, `b`, `n`) to UCI string upon selection.
4. **Massive Game PGN Import (>150 Moves):**
   * Limit Stockfish batch depth to 14 if game length exceeds 100 moves to guarantee total review completion under 30 seconds.

| **Groq** | `llama-3.1-70b-versatile`, `mixtral-8x7b-32768` | `groq` Python SDK / OpenAI-compatible REST | Ultra-fast inference ($\le 200\text{ms}$), JSON mode support |
| **OpenRouter** | `anthropic/claude-3.5-sonnet`, `deepseek/deepseek-r1`, `meta-llama/llama-3.1-70b-instruct` | `https://openrouter.ai/api/v1/chat/completions` | Universal model aggregation, fallback routing |

#### 1.2 Adapter Interface Design (Python Pseudocode)

```python
# Interface for All Provider Adapters

class BaseLLMAdapter(ABC):
    
    @abstractmethod
    async def generate_narrative(
        self, 
        payload: SynthesisPayloadModel, 
        system_prompt: str, 
        api_key: str, 
        model_name: str
    ) -> CommentaryOutputModel:
        """Executes API call, enforces JSON response schema, returns structured model."""
        pass

    @abstractmethod
    async def test_connection(self, api_key: str, model_name: str) -> ProviderHealthResult:
        """Executes a live test call with a dummy payload and measures performance."""
        pass
```

### 2. DETAILED PROVIDER ADAPTER IMPLEMENTATIONS

#### 2.1 Groq Adapter Implementation
- **SDK Usage:** `from groq import AsyncGroq`
- **Request Parameters:** `temperature=0.2`, `response_format={"type": "json_object"}`, `max_tokens=400`.
- **Special Handling:** Groq requires strict system prompt enforcement to output valid JSON.

```python
# Groq Adapter Logic
CLASS GroqAdapter(BaseLLMAdapter):
    ASYNC FUNCTION generate_narrative(payload, system_prompt, api_key, model_name):
        client = AsyncGroq(api_key=api_key)
        
        response = AWAIT client.chat.completions.create(
            model=model_name,
            messages=[
                {"role": "system", "content": system_prompt + "\nOUTPUT MUST BE VALID JSON MATCHING SCHEMA."},
                {"role": "user", "content": payload.model_dump_json()}
            ],
            temperature=0.2,
            max_tokens=400,
            response_format={"type": "json_object"}
        )
        
        raw_json = response.choices[0].message.content
        RETURN PARSE_AND_VALIDATE_JSON(raw_json)
```

#### 2.2 OpenRouter Adapter Implementation
- **HTTP Endpoint:** `POST https://openrouter.ai/api/v1/chat/completions`
- **Headers Required:**
  - `Authorization: Bearer <OPENROUTER_API_KEY>`
  - `HTTP-Referer: https://caissaxai.com` (App identification)
  - `X-Title: CaissaXAI Chess Engine`

```python
# OpenRouter Adapter Logic
CLASS OpenRouterAdapter(BaseLLMAdapter):
    ASYNC FUNCTION generate_narrative(payload, system_prompt, api_key, model_name):
        headers = {
            "Authorization": f"Bearer {api_key}",
            "HTTP-Referer": "https://caissaxai.com",
            "X-Title": "CaissaXAI",
            "Content-Type": "application/json"
        }
        
        body = {
            "model": model_name, # e.g. "anthropic/claude-3.5-sonnet"
            "messages": [
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": payload.model_dump_json()}
            ],
            "temperature": 0.2,
            "response_format": {"type": "json_object"}
        }
        
        response = AWAIT httpx_post("https://openrouter.ai/api/v1/chat/completions", headers=headers, json=body)
        raw_json = response.json()["choices"][0]["message"]["content"]
        RETURN PARSE_AND_VALIDATE_JSON(raw_json)
```

#### 2.3 Google AI Studio (Gemini) Adapter Implementation
- **SDK Usage:** `google.genai` SDK or Direct REST API (`v1beta`)
- **Endpoint:** `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent?key={API_KEY}`
- **Structured Output Config:** `response_mime_type="application/json"`

```python
# Google AI Studio (Gemini) Adapter Logic
CLASS GoogleGeminiAdapter(BaseLLMAdapter):
    ASYNC FUNCTION generate_narrative(payload, system_prompt, api_key, model_name):
        # Configure Gemini Client
        url = f"https://generativelanguage.googleapis.com/v1beta/models/{model_name}:generateContent?key={api_key}"
        
        body = {
            "contents": [{
                "parts": [
                    {"text": system_prompt + "\n\nJSON PAYLOAD:\n" + payload.model_dump_json()}
                ]
            }],
            "generationConfig": {
                "temperature": 0.2,
                "responseMimeType": "application/json"
            }
        }
        
        response = AWAIT httpx_post(url, json=body)
        raw_json = response.json()["candidates"][0]["content"]["parts"][0]["text"]
        RETURN PARSE_AND_VALIDATE_JSON(raw_json)
```

### 3. LIVE INTEGRATION TEST HARNESS & HEALTH DIAGNOSTIC SUITE

The system must feature an automated, end-to-end diagnostic runner that tests any provided API key against a benchmark chess position.

#### 3.1 Diagnostic Test Protocol
When a user inputs an API key or clicks **"Test Integration"** in the UI:
1. System loads a static benchmark payload (`BENCHMARK_TEST_PAYLOAD`):
   - Position: Italian Game (`1. e4 e5 2. Nf3 Nc6 3. Bc4 Nf6 4. Ng5`)
   - Move: `4... d5`
   - Deltas: `center_control_delta: +20`, `threats_cp: +50`
2. Measures API connection latency ($\text{ms}$).
3. Verifies HTTP status $200$.
4. Validates returned output against `CommentaryOutputModel` schema.
5. Runs **Anti-Hallucination Filter** on the returned commentary text to ensure moves cited exist in the legal move pool.
6. Returns a structured `ProviderHealthResult`.

```python
# Diagnostic Suite Schema
class ProviderHealthResult(BaseModel):
    provider_id: Literal["groq", "openrouter", "google_gemini", "openai", "anthropic"]
    model_name: str
    status: Literal["SUCCESS", "INVALID_KEY", "RATE_LIMITED", "SCHEMA_ERROR", "HALLUCINATION_DETECTED", "TIMEOUT"]
    latency_ms: float
    error_message: Optional[str] = None
    sample_narrative: Optional[str] = None
    tested_at: str
```

### 4. DYNAMIC PROVIDER SETTINGS & SECURE KEY VAULT (UI & BACKEND)

#### 4.1 Client-Side API Key Vault (UI State)
The UI MUST allow users to input keys for multiple providers and select the active provider dynamically during gameplay or review.

```typescript
// Provider Configuration State Interface (Zustand)

export type ProviderID = 'groq' | 'openrouter' | 'google_gemini' | 'openai' | 'anthropic';

export interface ProviderConfig {
  apiKey: string;
  selectedModel: string;
  status: 'UNTESTED' | 'TESTING' | 'HEALTHY' | 'ERROR';
  latencyMs?: number;
  errorMessage?: string;
}

export interface ProviderStoreState {
  activeProvider: ProviderID;
  providers: Record<ProviderID, ProviderConfig>;

  // Actions
  setActiveProvider: (provider: ProviderID) => void;
  setProviderKey: (provider: ProviderID, key: string) => void;
  setProviderModel: (provider: ProviderID, model: string) => void;
  testProviderConnection: (provider: ProviderID) => Promise<boolean>;
  testAllProviders: () => Promise<void>;
}
```

#### 4.2 Security & Key Storage Rules
1. **Client-Side Masked Persistence:** API keys stored in `localStorage` must be masked (`grk_••••••••1234`) when displayed in input fields.
2. **Encrypted Header Transmission:** When calling the backend API, the client passes the active provider ID and keys via custom HTTP Headers:
   - `X-Caissa-Provider: groq`
   - `X-Caissa-ApiKey-Groq: gsk_...`
   - `X-Caissa-ApiKey-Gemini: AIzaSy...`
   - `X-Caissa-ApiKey-OpenRouter: sk-or-...`
3. **Zero Backend Database Persistence:** API keys must NEVER be saved to the backend database. They exist strictly in the client's volatile state/local vault and are passed in headers per session request.

### 6. WORKFLOW & SEQUENCING (KEY VERIFICATION TO NARRATION)

The full sequence from UI key input to live commentary generation is shown below:

```
[User Types API Key in Settings UI]
        │
        ▼
[User Clicks "Test Connection"]
        │
        ▼
[Frontend sends POST /api/v1/providers/test with Header: X-Caissa-ApiKey-Gemini]
        │
        ▼
[Backend Gateway receives test request]
  ├── Instantiates Target Adapter (e.g. GoogleGeminiAdapter)
  ├── Loads Benchmark Chess Payload (Italian Game 4...d5)
  ├── Starts Timer
  ├── Executes API Call -> Receives JSON
  ├── Measures Latency (ms)
  ├── Runs JSON Schema Validation
  └── Runs Anti-Hallucination Filter on output text
        │
        ├─── [FAIL] ──► Return ProviderHealthResult(status="ERROR", message="...")
        │                UI renders RED Badge 
        │
        └─── [PASS] ──► Return ProviderHealthResult(status="HEALTHY", latency_ms=210)
                         UI renders GREEN Badge  (Shows 210ms)
        │
[User plays move on Chessboard]
        │
        ▼
[Frontend sends Move Request using ACTIVE Provider Selection & Headers]
        │
        ▼
[Backend routes to active provider adapter -> Returns live, verified commentary]
```
